# MegaMoE 准备阶段与设备路由验证（2026-11-28）

本记录补充[上一阶段报告](megamoe_preparation_20261127.md)。区分已完成的跨机实验、最终候选的正确性检查和仍待运行的性能实验，不把不同版本的阶段收益相加。

## 比较边界

准备窗口统一为计数 AllGather 设备结束到 MegaKernel 设备开始，包含窗口内计算、同步及 Free。Free 是设备时间线的空隙，不能直接解释为 Host 执行时间或内存释放时间。

完整调用使用关闭 profiler 的 NPU event；前向、重计算、反向分别统计。每次先取全部 rank 最大值，再对样本取 P50。准备窗口是另一次带 profiler 的采集，不能将两个窗口相减来估算某个函数的成本。

规格为每 rank 4096 token、隐藏维度 5120、专家中间维度 1792、TopK8；EP64、384 专家，每 rank 六专家。Pull、通信切分 4096、ready lookahead 1，通信仍为 BF16。此实验没有共享专家、FSDP、优化器或完整模型，不直接代表整网 MFU。

## 原始问题与路径边界

历史 MXFP8 样本的 Permute 结束至核心开始曾有 1.642 ms 间隔，包含计数后处理与回读、精确元数据生成、激活分配、启动描述序列化、字节视图包装和原生提交。该间隔既不是纯量化时间，也不是纯 CPU 时间。历史版本已先异步发起计数 AllGather，再提交 Permute，不能描述为一律先 Permute 再 AllGather。

冻结上游基线为 `d114947294071b575c0acda29ce3b45c2820d83e`。其大输入 Pull 路径在回读真实接收量并确认容量后才直接排列到 SHMEM；普通显存提前排列受大小阈值限制。默认优化将计数后处理、摘要异步回读与输入排列放在独立设备依赖链上，最终仍校验真实计数并精确分配。

本次实现分为两部分：

| 部分 | 默认行为与适用边界 |
| --- | --- |
| 公共优化（exact） | 保留计数摘要 D2H、Host 校验和精确接收激活；共享元数据计算、桥接函数入口缓存和 MXFP8 描述缓存优化。不同 EP rank 可使用不同输入长度。 |
| 显式设备路由（budget） | 设置 `HYPER_MULTICORE_MEGAMOE_DEVICE_ROUTE=1` 才启用；Pull、本轮各 rank 输入长度相等、真实接收量不超预算。默认系数 `1.05`，设备逐次校验真实计数、参与状态和接收容量，不复用 fix-router 计数。 |

预算为 `max(128, align128(ceil(min(factor, EP) × T × top_k)))`，各次调用的 `T` 可变化。源 SHMEM 按已知展开输入准备；完整专家激活按预算持有到对应反向结束。超预算或非法计数明确终止，不截断 token，不静默回退。VLM 等 rank 间不等长输入暂不支持预算路径，默认精确路径保持原支持。

默认摘要与预算入口互为替代，不会先摘要 D2H 再执行预算入口。两个入口复用同一套设备元数据计算；预算校验通过独立策略注入，默认入口没有预算容量前提。

## 已完成的 EP64 实验

源和适配库均冻结的上游 master、公共优化 exact、上一轮 budget 在同一作业比较。每版本两轮、每轮三组 50 次无 profiler 样本，共 300 次；保留所有样本。以下为完整调用 P50，单位 ms，单元格依次为前向 / 重计算 / 反向。

| 精度 / 路由 | master | exact | budget |
| --- | --- | --- | --- |
| BF16 / 固定 | 8.1832 / 8.1618 / 10.3021 | 7.7844 / 7.7029 / 10.3072 | 7.5736 / 7.3934 / 10.2965 |
| BF16 / 随机 | 8.0117 / 7.9973 / 10.3199 | 7.7423 / 7.6103 / 10.3412 | 7.3780 / 7.2515 / 10.3473 |
| MXFP8 / 固定 | 8.4989 / 8.4818 / 7.3084 | 7.9423 / 7.9203 / 6.9437 | 7.6124 / 7.4458 / 6.9654 |
| MXFP8 / 随机 | 8.4797 / 8.4199 / 7.3186 | 7.9160 / 7.8048 / 6.9238 | 7.5519 / 7.3738 / 6.9253 |

这些是最终候选之前的结果。相对 master，exact 的完整前向降低约 3.4%–6.7%，budget 降低约 7.4%–10.9%；不是整网收益，也不是本轮最终候选的新增收益。

同一次采集的 rank48 原始 CANN 准备窗口 P50，单位 μs，单元格依次为前向 / 重计算：

| 精度 / 路由 | master | exact | budget |
| --- | --- | --- | --- |
| BF16 / 固定 | 745.0 / 761.6 | 414.2 / 449.3 | 51.0 / 59.3 |
| BF16 / 随机 | 743.9 / 761.4 | 504.2 / 536.7 | 48.2 / 48.5 |
| MXFP8 / 固定 | 1184.5 / 1169.3 | 636.6 / 638.0 | 271.2 / 356.9 |
| MXFP8 / 随机 | 1154.9 / 1148.4 | 798.6 / 690.4 | 195.8 / 182.7 |

不能据 rank48 得出固定路由普遍更慢。其他 rank 的差异方向不一致。该 rank 的 MXFP8 budget 固定/随机前向相差约 75.36 μs，计算覆盖接近，差异主要体现为 Free；字节 view 的 Host 覆盖只相差约 4.51 μs，不能将整段 Free 全归因于 view。

元数据核独立测试约从 73.5 μs 缩短到 44–45 μs，但与 Permute 同时提交时可能争用 AIV。更快的单核也未使所有完整调用稳定加速。此前合并张量分配的 Host 候选没有稳定收益，未纳入最终候选。

## 最终候选具体变更

1. **预算元数据排在生产者之后。** 计数 AllGather 继续走准备流，Permute 在调用流；激活和计划准备与生产者重叠，调用流等待计数交换后才提交 Metadata。Metadata 不再与本次 Permute 争用 AIV。默认 exact 路径不强加这项顺序。
2. **MXFP8 直接构造原生字节描述。** 复用 torch-npu 原生 TensorStruct 转换和 ACLNN 提交，在一次调用内构造字节单位描述，省去前向/反向 27/33 组 ATen dtype-view/reshape 包装。描述逐次绑定真实地址，保留存储偏移、边界、allocator、队列和 stream 语义；非稠密物理格式沿用原 dtype-view 转换，不重写数学算子。
3. **启动描述先查缓存再序列化。** 只缓存不可变存储大小和几何边界，容量、设备、token 覆盖或事件边界变化时使用不同键；继续保留跨流 ready 事件和 `record_stream`。不缓存当前计数、激活或 FSDP 权重地址。
4. **桥接缓存公共化。** 仅缓存可执行函数地址，内存上下文初始化、释放和清理仍逐次执行；V1/V2 保留原生提交路径。

没有改变通信字节、SHMEM 版本、数值 task、专家粒度、精度配方或梯度语义。没有新增分配工厂。MXFP8 源码与 adapter 须匹配 ABI4。

## 最终候选验证与验收计划

Ascend950DT 双卡完整规格检查通过 20 组 BF16/MXFP8、固定/随机、冻结基线与候选组合，V2 队列执行前向、重计算和反向；另两组 MXFP8 V1 队列通过。每组均检查数值和有限值，采集 rank0 的输出/梯度签名与对应 master 共 22 组逐字节一致。跨版本逐字节比较范围是采集的 rank0，不能声称覆盖全部 rank。

另外两项设备训练用例通过，覆盖每次调用长度变化、空输入、空专家、权重物理双轴更新和多个待反向上下文。最终 CPU 回归 235 项通过（无跳过）；仓库检查通过，解析 302 个 Python 文件、核验 13 个锁定补丁，无失效路径或下游导入。CPU 检查覆盖字节描述与真实 storage/offset 一致、每次调用所有权、缓存命中与边界失效；设备验证不由 CPU stub 替代。提交顺序调整后同步更新 CPU 替身的 stream 合同，错误传播和无读回分支均通过。

双卡环境为 Python 3.11.10、PyTorch 2.12.0+cpu、torch-npu 2.12.0.post3.dev20261116、CANN 9.3.0；适配库在 CANN 9.2.2 环境编译。双卡短采样只证明已执行范围的正确性与可运行性，不作为最终性能发布依据，不能替代 CANN 9.2.0 集群验收。

待运行 EP64 最终实验保留未修改 master、冻结 exact/budget，增加 serial-budget、final-exact、final-budget，固定/随机配对，三轮调整版本顺序以减小时间漂移。每轮 25 次预热、三组 50 次无 profiler 测量，合计 450 次；保存全部 rank 样本并选真实尾部 rank。第一轮另外采集 Level0 CANN 和独立 Host 归因，关闭 `record_shapes`、memory 和 stack。

新增边界为算子入口/返回、命令 Enqueue/Dequeue 及设备开始相对 AllGather 结束的有符号时间；区间允许重叠，不强行相加。输出先在私有临时文件生成完整 JSON，再发布并核验 SHA，避免原始 trace 被上传为未完成文件。

最终候选的新增性能收益尚未验收。完成 EP64 后同时比较准备窗口、AllGather 到核心结束、完整前反向和最慢 rank；再决定是否接受该候选及是否需要继续优化。后续完整 PanGu、动态不等长 token、FP8 通信、Wave 和共享专家融合属于独立验证工作。
