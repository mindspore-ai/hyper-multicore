# MegaMoE 准备阶段优化与验证报告

日期：2026-11-27。本文记录准备路径优化、Permute 桥接回退的定位和现有性能边界，不作为全量网络性能承诺。

## 问题与比较边界

MegaMoE 在路由计数交换后，仍需完成真实计数回读、校验、精确激活分配、参数绑定和原生算子提交。
这些 Host 工作会在设备时间线上表现为核心启动前的间隔。
本轮目标是在保持动态路由和完整训练语义的前提下，减少串行准备与重复桥接开销。

准备窗口统一为“计数 AllGather 设备完成 → Dispatch AllToAllV 或 MegaKernel 设备开始”，保留区间内实际的 Free、Permute 和分配。
不再使用 Permute 结束作为主窗口起点，也不把 Host 回读 API 的等待时间称为纯 D2H 时间。

两种窗口的工作边界仍有区别：native 风格控制在第一次 Dispatch 开始时结束，部分专家计算准备发生在 Dispatch 之后；
MegaMoE 需要在融合 kernel 启动前准备完整专家流水的缓冲和参数。因此准备窗口之差不等于全部可删除的工作。
完整前向、核心结束时间和准备窗口必须一起判断，不能仅凭 kernel 提前启动推导端到端收益。

## 实现方案

| 位置 | 本次改动 |
| --- | --- |
| `modules/mega_moe/route.py`、`workspace.py` | 在资源所属旁路流中统计、交换计数，准备描述符与异步摘要回读；调用流独立 Permute，并维护输入、描述符和异常退出的 stream 依赖。 |
| `ops/common/mega_moe/utilities.asc`、`torch/csrc/mega_moe_utilities.cpp` | 扩展已有辅助算子，在 UB 容量允许时一起生成行/元素偏移与本轮摘要；BF16 前后向张量按真实行数集中分配。 |
| BF16、MXFP8 后端及 Torch 接口 | 复用只读启动描述、元素视图和设备架构信息；MXFP8 在 C++ 构造无拷贝字节视图。 |
| Pull 源缓冲准备 | 已有 SHMEM 源缓冲容纳本卡 `T×K` 行时，短租约内 Permute 直接写入，与计数准备重叠；若容量确认后 owner 被替换，则在新 owner 上重新 Permute。 |
| `torch/csrc/moe_token_permute_out.cpp` | 复用 `aclnnMoeTokenPermute`，缓存内存上下文辅助函数入口，消除扩展桥接的重复符号查找；逐次初始化、释放与清理照常执行。 |

不缓存真实路由计数、激活、当前权重或 SHMEM 地址。固定路由与逐轮变化路由都消费本次真实计数。
摘要事件完成后才读取 Host 数据、校验并提交容量；提前写入不发布远端可消费信号。
不新增最坏接收量预留池。专家输入、激活和待反向状态仍属于各次调用，旧 ctx 不被后续层或调用覆盖。

普通摘要为 `[EP, 8]` 的 int64，EP64 时为 4 KiB。`host.tolist()` 消费已完成异步回读的 CPU 张量，本身不是第二次 D2H。
原 native 风格控制回读两个 EP 长度的发送/接收列表；两者内容不同，不能把 Host 等待差简单解释为数据大小差。

MXFP8 桥接 ABI 从 3 更新为 4；Python 源码与原生 adapter 必须一起重建，不能与旧 payload 混用。
构建按[构建指南](../build.md)执行。本轮未替换数学 kernel、通信引擎、SHMEM 依赖或任务调度顺序。

## 环境与统计方法

实测设备为 Ascend910_93（arch2201，Atlas A3系列产品），Linux aarch64；Python 3.11.14、PyTorch 2.12.0+cpu、torch_npu 2.12.0、CANN 9.1.0。
性能用例为 BF16、Pull、真实 EP4，每卡 `N=4096`、`H=5120`、`I=1792`、全局 `E=24`、`TopK=8`，每卡 6 专家。
前向在 `no_grad` 下执行，8 次预热、10 次测量，不删除异常点。

完整前向关闭 profiler，每次同步后计时；准备窗口另用 CANN Level0 trace 提取。
主表每次取四个 rank 的最大值，再取 P50。逐次分段表将 40 次 rank 调用分别取 P50，不能与主表拼接相减。
新旧各版本使用同一组设备和同一配套 payload，路由 fixture 哈希一致，固定、变化、空专家场景均做独立数值对照。
native 为独立 BF16 AllGather/AllToAllV 控制实现，不是原 PanGu 作业，也不是全网 native 性能基线。

## 已观察到的收益

### 双流准备

相对于本轮早期串行准备版本，双流版本在一次同卡对照中得到以下结果，单位为 ms：

| 路由 | 准备窗口：串行 → 双流 | 完整前向：串行 → 双流 | 完整前向耗时降低 |
| --- | --- | --- | --- |
| 固定 | 2.3501 → 1.1936 | 10.2455 → 9.5108 | 7.17% |
| 变化 | 2.1190 → 1.0005 | 9.9746 → 9.5326 | 4.43% |
| 存在空专家 | 2.2855 → 1.2364 | 12.3422 → 11.6865 | 5.31% |

这是阶段性实现对照，包含流水与排列入口/存储组织的变化，不能全部归因于纯双流重叠，也不能直接当作本 PR 相对上游 master 的最终收益。
该双流阶段先 Permute 到普通显存再复制到 SHMEM；空专家冷 rank 曾增加约 280.72 MiB 的 allocated 峰值。
后续直写方案消除这份输入临时结果及复制，仍保留精确接收激活分配。

### 直写回退与函数地址缓存

直写复用仓库已有的输出地址接口，并未重写 Permute 数学。最初完整前向反而变慢约 5%–8%。
定位发现扩展 V1 桥接每次重新解析 `InitHugeMemThreadLocal`、`ReleaseHugeMem`、`UnInitHugeMemThreadLocal`，原生 op-plugin 则缓存这些函数地址。
只改变函数地址缓存的独立共享库对照消除了这一回退。

单卡无 profiler 的 30 次采样中，普通 HBM 输出的 Host P50 从 216.162 μs 降至 28.770 μs，SHMEM 输出从 183.397 μs 降至 22.366 μs。
多卡 trace 中，未缓存直写的 Permute Host P50 约 912–958 μs，缓存后约 67–78 μs，与普通 Permute 的约 64–70 μs 接近。
函数查找可能受线程并发放大；主线程与 worker 的时间不能直接相加。

下面为同一轮三版本完整前向 P50，单位 ms：

| 路由 | 双流＋普通 Permute＋Copy | 直写、未缓存桥接 | 直写、缓存桥接 | 缓存直写相对双流的耗时变化 |
| --- | --- | --- | --- | --- |
| 固定 | 9.5431 | 10.0238 | 9.5364 | -0.07% |
| 变化 | 9.5390 | 9.9862 | 9.4990 | -0.42% |
| 存在空专家 | 11.6512 | 12.3870 | 11.7136 | +0.54% |

缓存后的结果恢复到双流基线附近，尚未证明直写有稳定的完整前向增益。
本轮缓存修复仅落在 Permute 入口；其他 MegaMoE C++ 入口的同类重复查找尚未统一整改。

### 为什么删除 Copy 不等于减少同样的前向时间

原先每次源复制约 0.58 ms、逻辑数据 320 MiB，但大部分已被 Host 后续准备掩盖。
以核心命令完成入队为界，固定路由 40/40 次复制已完成；变化路由 16/40 次已完成，剩余复制尾部 P50 仅 14.165 μs；空专家 27/40 次已完成，尾部 P50 为 0。
该边界只提供复制尾部的观察上界，不是可直接扣除的端到端时间。

一个对应样本中，删除 Copy 后核心开始提前约 0.136 ms，但 kernel 跨度从 6.788 ms 变为 6.920 ms，
相对 AllGather 的核心结束时间从约 7.650 ms 变为 7.646 ms。仅凭 CANN 整 kernel 边界不能区分内部等待、peer 就绪和缓存状态。
因此本报告不把这段跨度变化归因为通信或计算退化。

## 与 native 的剩余差距

在上述三版本对照中的缓存直写轮，准备窗口主口径结果如下，单位 ms：

| 路由 | native 风格控制 | 双流＋Copy | 缓存直写 |
| --- | --- | --- | --- |
| 固定 | 0.6537 | 1.3918 | 1.8461 |
| 变化 | 0.7821 | 0.9719 | 1.1430 |
| 存在空专家 | 0.7112 | 1.1004 | 1.7423 |

删除 Copy 并未消除最慢 rank 的准备尾部，部分场景该指标更差。上述 native 与缓存直写的差值约 0.36–1.19 ms，
既包含两种提交边界不同带来的必要准备，也包含 Host 与 rank 尾部，不能当作已经定位的可删除开销。

缓存直写同一批 trace 的逐次调用分段 P50 范围为：

| 分段 | P50 范围 |
| --- | --- |
| AllGather 设备结束 → 摘要 DMA 完成 | 约 0.014 ms |
| DMA 完成 → BF16 专家缓冲分配入口 | 约 0.25–0.30 ms |
| BF16 缓冲分配接口 | 约 0.03–0.04 ms |
| 缓冲返回 → MegaMoE C++ 接口入口 | 约 0.11–0.12 ms |
| MegaMoE C++ 接口入口 → 核心命令入队 | 约 0.36–0.42 ms |
| 命令入队 → 设备核心开始 | 约 0.03–0.04 ms |

这些独立中值不能直接相加。DMA 后的一段同时包含 Host 恢复执行、读取和验证及资源处理，不是纯计数校验成本。
核心桥接段是下一步优先对象；激活分配已经集中处理且数值很小，不计划为此引入最坏接收量预留池。

## 验证范围

此前冻结实现已完成以下验证：

- 双流阶段：196 项相关 CPU 检查与 7 项统计器检查；67 项 A3 路由辅助检查、Push/Pull 基础各 4 项设备检查，以及动态增长和自动布局检查。
- 提前直写阶段：87 项相关 CPU 检查及 4 项设备回归，覆盖动态输入、精度、容量/旧激活、共享资源与流生命周期。
- 缓存桥接对照：4 项设备回归通过，143.40 秒；14 个 worker 累计 1123 次调用修复入口，覆盖增长、空输入、旧 ctx、梯度、SGD、跨流与错误恢复。
- 路由辅助的 EP64 测试仅覆盖单卡输入表规格，不能称为真实 EP64 通信验证。

缓存桥接的设备对照通过独立命名空间共享库注入，仅改变对应入口，未替换原始 payload；没有测量共用桥接全面缓存后的收益。
本 PR 将已验证源码整理到上游 `d114947294071b575c0acda29ce3b45c2820d83e`，保留其 GLU 和构建改动。
整理后执行了 118 项相关 CPU 检查，全部通过（新增准备/统计及原生接口 41 项，路由、workspace、资源、自动微分、GLU 和 Torch 回归 77 项）；
仓库检查通过，解析 296 个 Python 文件、验证 13 个锁定补丁，没有下游导入或失效路径。
Permute 桥接文件使用配套 Torch/PTA/CANN 头文件编译通过。
额外执行的 Pylint 与 Lizard 尚未通过：前者包含许可证头、类型标注、文档字符串及格式问题，后者报告 6 处复杂度/长度告警。
这些检查结果与功能验证分开记录，不将本轮整理描述为门禁已通过。
以上实卡结果来自整理前冻结版本，不是整理后整套原生库重新构建和实卡运行的证明。
未验证 Ascend950、跨机 EP64、MXFP8 设备数值与性能、V2 task queue 或完整 PanGu 网络 MFU；MXFP8 当前只有 CPU 编译、别名与接口检查证据。

## 复现入口

先按[构建指南](../build.md)重建并激活当前源码及匹配 adapter，使用已有设备调度器取得四张空闲卡。
下列 worker 仅由仓库 launcher 执行，不属于默认自动收集的设备门禁；launcher 持有设备锁并限制运行时间。
`ASCEND_RT_VISIBLE_DEVICES` 填入调度器实际分配的物理设备，不应占用已有训练进程的卡。

```bash
export HMC_PREP_OUTPUT=/tmp/megamoe-preparation-result
export HP_MEGAMOE_DISPATCH=pull
python - <<'PY'
import os
from tests.common.port_utils import allocate_port
from tests.common.multicore._case_launcher import run_multicore_case

os.environ['HYPER_MULTICORE_SHMEM_BOOTSTRAP_ENDPOINT'] = f'tcp://127.0.0.1:{allocate_port()}'
run_multicore_case('tests/torch/_benchmark_mega_moe_preparation.py',
                   'test_preparation_window', num_proc=4,
                   timeout=1200, device_timeout=30)
PY
```

输出包括每个 rank 的原始 Chrome trace、完整前向原始样本、准备窗口及分配器峰值。
跨 rank 汇总须按相同调用序号先取最大值再取 P50，不以“各 rank 的 P50 最大值”替代。
不同版本应串行使用同一批设备，核对输入哈希与实际导入源码，并保留独立的 profiler/无 profiler 结果。
CPU 统计器检查为 `python -m pytest tests/ut/modules/mega_moe/test_preparation_metrics.py -q`。

   当前核心入队前约 0.36–0.42 ms，可把压到约 0.10–0.15 ms 作为待验证目标，不能写成已有收益。
2. 拆解 DMA 完成后的 Host 恢复、校验和资源处理，把只依赖静态规格的工作提前，减少重复查询和对象构造。
   不缓存路由结果，不绕过当前计数验证，不引入接收预留池。

4. 与真实 PanGu native 做同等范围的对照，同时比较准备窗口、AllGather 到核心结束和完整前反向。

5. 在相同输入、动态路由和生命周期回归通过后，再验证 Ascend950、MXFP8、跨机 EP64 及整网收益。
