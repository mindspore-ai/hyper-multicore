# 架构与代码归属

适用于本包所有组件、设备架构和框架接入。这里规定代码应如何组织；实现步骤见[变更流程](../workflows/change.md)，验证入口见[验证映射](../references/validation-map.md)。下述路径均相对 `hyper_multicore/`，表示目标职责，存量代码未必已完全符合。

框架当前的组成、执行机制和状态管理见[系统架构](../../docs/architecture.md)；本文用于判断修改应遵守的职责与正确性约束。

## 职责与依赖方向

职责分离首先是知识和状态有明确归属。简单流程可以直接实现；只有职责、变化原因或复用关系确实不同，才增加独立边界。`plan / graph / workspace / function` 是概念，不是新组件必须创建的文件清单。调用方应使用明确输入和结果，不拼接内部初始化顺序或解释私有布局。

组件可以依赖通用机制；通用机制通过显式参数接收任务、容量和地址，不反向导入组件，也不解释专家、概率、模型阶段或业务张量端口。计算 provider 与通信 provider 是并列能力，不要求每个组件都走通信路径。

| 位置 | 应集中的知识与状态 |
| --- | --- |
| `__init__.py`、公共选项 | 公共导出与接口边界；导入不触发初始化、编译或设备探测 |
| `modules/<component>/` | 接口与模型参数持有、数值选择、逻辑图、编排及资源需求；当前调用的输入绑定、launch、保存/恢复和梯度 |
| `modules/<component>/backends/`（确有需要时） | 不同数学/精度的执行与保存方式；共享生命周期不重复实现 |
| `scheduler/` | 通用图、任务、事件和队列的表示、排序、核放置、校验与序列化 |
| `tasks/` | 算子 typed 参数、lowering 与数学 tiling 的调用适配 |
| `torch/` 等框架目录 | binding、注册、参数与 stream 对接，不构造第二套业务图或实现设备数学 |
| `ops/runtime/` | 队列、ready 选择、事件、task 分发和通用诊断 |
| `ops/common/<component>/`、`ops/common/` | 前者共享组件设备逻辑；后者只放可跨组件复用的参数编码与原语 |
| `ops/hyper_*/op_host/`、`op_kernel/` | 前者负责 native ABI、外层校验、workspace 和 launch tiling；后者负责入口、task 分发与标准算子适配 |
| `shmem/` | 通用传输、引擎、QP、可见性与通信资源生命周期 |
| `_build/`、`ops/patches/` | 锁源、隔离组装、架构选择和制品；最小适配补丁按算子与用途命名 |
| `diagnostics/` | 通用观测；组件提供业务名称与解释。组件支持的诊断模式复用正常执行的数学、调度和完成机制，具体采集能力由组件接入合同决定 |

## 状态、配置与资源归属

### 配置和计划缓存

数值选项只解释一次；默认值、显式设置和环境变量的优先级集中处理，各层消费确定的有效值。最终生效配置应能通过所属对象或已有诊断入口查询，避免调用方重新推导。硬件确有差异时允许不同默认值，不强行统一核数或数值。执行配置与通信 engine 分开，避免借字段承载无关行为。

`plan` 是可复用的编译结果，不增加一层业务状态。共享 plan 的编译内容在发布后保持只读；调用、自动微分、框架桥接和诊断所需的变化放在独立的本轮状态或派生副本中。stream 登记等生命周期信息由资源所有者维护，与编译内容区分。

缓存 key 或可靠失效机制应区分**同一缓存内会变化、且影响编译结果**的输入，包括数学、布局、架构、lowering 和编排。固定输入无需机械重复入 key，但须由设置、更新和清理路径证明固定；缓存归属变化时重新判断。

构造时赋值不足以证明永远不变；把所有配置塞入 key 也不能补偿漏掉输入数据变化。路由、激活、当前权重/scale root、地址、stream 和 ctx 属于本轮调用，不缓存进静态 plan。沿缓存的创建、查询、更新和清理路径确认实际维护者，而非依赖某个字段名或文件位置。

### workspace 与调用生命周期

组件计算所需空间，资源管理代码协调分配、租用、重绑与释放；调用方不必掌握内部步骤。一次调用的保存内容不能被模块的“最新状态”替代。旧 ctx、重算、并发 stream、FSDP 参数重建和共享 workspace 均须保持存储有效，不能由缓存命中推断安全复用。

资源重建由组件给出物理需求和必要前置条件，通信机制不解释模型容量关系。物理分配身份和组件使用权有不同生命期，不合并成一个含糊状态。

## 数值、任务编译与执行边界

数值决定 dtype、舍入、clamp、概率加权位置和梯度累加。lowering 决定逻辑工作如何形成 task、分块及生产者计数。编排只调整合法依赖内的顺序和核放置。调优保持完整工作量、输出覆盖、数值、可见性和生命周期。

组件逻辑图描述 tensor 的读写、实际依赖和数学阶段，不携带物理 QP 或通用 runtime 的私有布局；这些细节分别由通信机制和执行层封装。

批处理若改变 task 集合或粒度，事件阈值必须随实际生产者数量调整；空 task、冷分组、尾块和终止也不能丢掉必要信用。判断是否为纯重排，要核对 task 集合和事件写入，不能仅凭函数名或所在目录。

### ABI 与队列

- 同一物理 ABI 维护一套明确的字段与版本合同。不同语言的表示保持一致，不各自扩展语义；不因跨语言重复声明就自动引入代码生成机制。Python serializer、C++ reader 和设备消费方的宽度、offset、单位、flags、版本一致。索引、行数、元素数和字节数明确区分，保留实际需要的 64 位地址/偏移。
- runtime 维护一套版本化 header/队列协议，同一 ready 机制不保留两套独立开关。核参与、任务放置、扫描窗口和等待方式各自表达，窗口不等于队列容量。
- 数学 tiling 由算子/provider 决定，外层 launch tiling 与 task 内数学 tiling 分开；框架桥接不重写数学。

### 通信与完成

组件适配层把业务地址转为通用传输请求。每个物理队列的 post/quiet 由协议规定的参与方负责，不能把 AIV 奇偶当成固定硬件所有权。

提交返回不等于完成。消费者信用覆盖全部 payload 可消费的条件；混用搬运引擎时各自保证完成。源 buffer、接收 buffer 和 workspace 只有在相应使用结束后才能复用，不能用省略等待或工作量换取性能。

## 公共机制与组件特化

公共层接受明确的资源数量和操作参数，业务公式在组件内解释。例如专家容量由组件计算，公共层接收计算后的容量和边界；存量业务公式所在的位置不能成为新增业务策略的理由。

通用 task ID 和 typed descriptor 可以表示具体算子；判断边界看公共层是否解释模型阶段和路由关系，不看名称中是否含组件名。把业务字段改名为 `extra` 不会使它变通用。

迁出组件 tiling 解码时，以显式存储边界保留设备保护。Host 输入检查不替代设备 ABI、真实存储或异步状态的检查。

### 标准算子与适配

优先复用锁定 revision 的标准计算源码，只在隔离构建树应用补丁，不修改系统 CANN 或原始依赖仓。适配器负责 typed 参数、合法 tiling、逻辑核、局部资源初始化与收尾，不复制数学源码闭包，也不把完整独立算子的外层 launch 流程塞进每个 task。

标准来源不保证实际分支、模板、核数或性能与 native 相同；尤其全核同步和物理核编号不能直接套入 task。适配不能伪装数学重写。标准能力确实不足而临时自实现时，限定数值语义、缺口、验证和替换条件，例外留在组件内。相关依赖、能力或实现变化时重新核对缺口；上游已满足需求时按替换条件收敛，不因曾经获准就永久保留或扩散到 runtime。

## 修改既有边界时的取舍

先满足明确需求并保持仍适用的数值、ABI、完成和生命周期要求，再维护职责与依赖方向，复用正确的既有机制，最后优化 diff 大小和局部整洁度。真实的数学、硬件或保存差异优先于去重；共享方式见[代码质量](code-quality.md#直接实现与抽象)。

发现旧问题不自动启动整改。新增逻辑不扩大旧耦合；必须改变旧语义时，只拆出本次需要的最小边界。扩大公共接口或迁移现有调用方前，先核对更小接口能否满足需求，指出具体缺失能力和不调整的实际后果。

例如直接分配接口已能满足容量、校验和完成要求时，不为接入新组件先改造公共 builder；需要图分析或 lowering 时，再核对图构建路径的适用条件。

保留例外时明确原因、负责代码、影响、验证与退出条件；记录本身不豁免规则或替代本次必要的正确性工作。不为目录整齐搬动无关实现，不留下永久双主线兼容层。
