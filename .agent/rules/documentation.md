# 文档写法

正文按人的阅读顺序组织，agent 通过稳定标题、明确术语和准确链接找到同一份内容。无需把所有文档写成检查表。

## 先回答读者的问题

- 使用文档先讲用途、最小可运行用法和重要限制，再补参数与扩展场景。示例说明必要环境和适用范围，不把内部实现细节塞进用户操作步骤。
- 设计说明解释为什么这样做、关键取舍和最容易误解的地方。用具体对象描述：能说“谁创建和释放 workspace”，就不只写“明确资源所有者”。
- 模块说明交代职责；公共接口说明调用方无法从签名看出的行为、错误和资源责任。简单内部函数无需重复签名、类型或逐项填写说明；注释解释原因和不变量，不翻译代码。
- 段落各自推进一个问题，标题直接表达主题。并列比较用表格，步骤用列表，关系复杂时再用图；普通解释保留连贯正文。

## 事实与维护位置

当前能力、拟议设计和已验证结果明确区分。计划接口不能写成已支持用法，旧示例不能证明新能力；验证结论按[验证映射](../references/validation-map.md#证据与结论)限定范围。

架构要求维护在 [architecture.md](architecture.md)，用法和实现说明在所属组件及 `docs/`，运行方法在[测试指南](../../tests/README.md)和[构建指南](../../docs/build.md)。其他入口链接这些来源，不复制命令矩阵和规范全文。行为变化同步相关说明；内部重排只修改受影响内容。

一次任务的调查过程、临时限制和未决问题留在任务记录，不自动进入长期文档。只有已经稳定且对后续使用或维护有价值的决定，才整理到所属说明。历史报告标明版本和日期，不覆盖当前规则。

## 导航与维护

核心规则直接表达判断条件，不绑定具体实现文件、私有符号或普通单测。导航优先引用领域目录、公共接口说明和构建/测试指南；具有特殊执行条件的检查保留准确入口。链接写明阅读目的，长文仅在需要定向阅读时使用不依赖章节编号的主题标题。

文件、标题或接口变化时，检查引用方的路径、锚点与含义；更新或移除过期引用。具体源码示例留在所属实现说明，使用前核对当前调用链与适用条件，不把其布局、默认值或限制推广为通用要求。关键接口约定不明时先确认实际行为，不静默放宽规范。

修改指令先消除重复、歧义和失效指针，只有缺少判断依据时才增加规则。按[文档验证入口](../references/validation-map.md)检查链接和格式；行为试用未覆盖的部分如实保留，不以模板完整证明效果。
