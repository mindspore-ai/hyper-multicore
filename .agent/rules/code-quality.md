# 代码质量

默认选择是满足当前需求的直接实现。质量体现在调用和修改一项行为时需要理解的知识更少，不以说明篇幅、文件数或抽象层数衡量。职责和依赖见[架构规则](architecture.md)。

## 直接实现与抽象

- 新配置、类或扩展点解决当前存在的问题，不为假想后端预建策略系统。固定行为直接表达，不增加没有使用场景的可选分支。
- 抽象应集中已有的重复知识、封装资源生命周期，或隔离真实的外部差异。若调用方仍需了解同样的内部细节，优先保留直接实现。薄 adapter 有实际隔离作用即可，不因行数少而拆掉或因层次图而新增。
- 同一规则尽量只解释一次，改变它不应要求同步修改无关位置。相似代码若数学、保存或生命周期不同，保留差异，只共享确实相同的部分；不按实现数量机械决定抽象。

## 局部可读性与状态

- 正常路径容易顺着读完，分支对应实际行为差异。提前处理明确的失败或空情况，避免为假想输入嵌套多层条件。
- 避免多个布尔参数组合出难以理解的模式；使用能表达真实选择的参数或明确操作，也不为单一选择预建类型体系。
- 避免独立维护可直接推导的重复状态。为性能或设备执行需要缓存派生结果时，明确其来源、更新或失效方式，由同一所有者维护一致性。
- 提取函数应封装可命名的动作或规则，减少调用方需要知道的细节；不要把连续的简单流程拆成多层转发，也不为行数或复杂度阈值制造包装。

## 命名

- 名称在声明和调用位置都能理解，利用模块上下文保持简短。名称过长时先检查是否混合了多项职责。
- 歧义处标明对象和单位，如 `offset_bytes`、`num_rows`、逻辑核与物理核；上下文唯一的 `plan` 无需反复加组件前缀。
- 保留领域内明确的缩写。避免用实验代号、`extra`、`new`、`v2` 或泛化的 `manager`、`utils` 掩盖职责；协议版本和真实兼容层除外。

## 防护与错误

- 在用户输入、外部资源或状态变化的边界建立保证，内部直接沿用。规范化并验证过的配置按确定类型访问，不用 `getattr` 默认值、反复转换或宽泛异常捕获掩盖调用错误。
- 新校验对应新的风险或状态变化；删除校验须有仍然成立的上游保证。设备 ABI、存储边界和异步状态各有检查位置，不能因 Host 已验证就删去这些保护。
- 错误保留能定位问题的输入和操作信息；只捕获能够正确处理或补充上下文的异常。状态不明的资源不能吞掉异常后继续使用。
- fallback 必须有明确触发条件且保持承诺的语义，不静默换算法或隐藏不支持的能力。诊断可尽力执行，但失败隔离不能改变主操作结果或资源状态。

格式、许可证和工具检查沿用[仓库代码检查](../../README.md#代码检查)；测试写法与执行范围见[验证映射](../references/validation-map.md)。
