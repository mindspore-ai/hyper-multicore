# 变更流程

## 默认做法

1. 检查工作区已有修改和比较基线。依据用户要求或已确认的计划，明确本轮目标、要保持的现有行为和约定延后的工作。定位受影响的实现和调用方，按入口读取适用规则。
2. 在负责该行为的位置完成最小必要修改，优先使用正确的既有接口。实现选择遵循[架构](../rules/architecture.md)和[代码质量](../rules/code-quality.md)。根据变更影响，同步接口行为、使用说明或设计机制的对应文档；仅调整实现位置时，更新受影响的源码定位链接。
3. 交付前逐块核对最终 diff 与调用链。每处改动须对应本轮目标、兼容要求或必要验证。检查同组变量的命名、跨层依赖的方向，以及新增抽象和校验所解决的实际问题。撤回本次引入的无关改动，保留用户已有修改。
4. 按[验证映射](../references/validation-map.md)验证受影响行为，简述改了什么、检查结果和剩余限制。按用户授权处理提交与发布。

局部修改直接推进，不要求先写设计说明、逐项展示判断或创建任务文件。主要产物是清楚的代码和对应验证。

## 何时展开设计

新增公共能力、改变职责边界、存在实质方案取舍、涉及复杂状态/资源生命周期，或需要跨轮恢复时，才保留必要的设计说明；用几句话或[简短记录](../templates/change.md)即可，长度由未解决的问题决定。

说明只覆盖关键选择及理由。有未决前提时，区分已确定、条件成立后采用和待决，明确当前能推进的部分。数学、训练目标和资源持有权等不能凭名称猜定；先解决阻塞当前决定的问题，未纳入需求的后续能力不自动成为开工条件。调查或用于回答可行性问题的有界原型可以先做，依赖未决前提的正式实现不能自动提前。

实施中若新增公共接口、跨入新职责、改变原先保持的行为或产生第二份状态解释，先重新判断必要性，再继续依赖它的修改。已有决定未变化就继续执行，不重复展开设计。恢复工作时核对记录与实际 diff。

删除、改名或改变公共接口行为前，从[公共接口说明](../../hyper_multicore/README.md)核对该接口已有的稳定性约定，并检查已知消费者，按本次变更范围决定迁移或必要过渡。

调整接口时先落实边界，再迁移必要调用方和清理旧入口；不混改数学、传输、依赖版本与计时条件掩盖问题。记录用于帮助开发，不增加例行审批，也不赋予规则豁免。
